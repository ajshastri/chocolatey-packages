## Workflows

| Workflow | Status | What it does |
| --- | :---: | --- |
| sync | [![sync](https://github.com/ajshastri/chocolatey-packages/actions/workflows/sync.yaml/badge.svg)](https://github.com/ajshastri/chocolatey-packages/actions/workflows/sync.yaml) | Daily (and on demand): runs `chocotools sync` and opens or updates one PR from `bot/sync` into `master`. A branch whose PR was closed unmerged gets its PR opened again on every run; to discard those updates, delete the `bot/sync` branch (closing the PR alone is not enough). A branch already merged, or conflicting with `master`, is rebuilt from `master`; if that run finds no updates, a still-open stale PR is commented on and closed (`chocotools syncpr plan`). |
| ci | [![ci](https://github.com/ajshastri/chocolatey-packages/actions/workflows/ci.yaml/badge.svg)](https://github.com/ajshastri/chocolatey-packages/actions/workflows/ci.yaml) | On pull requests and pushes to `master`: pytest, `chocotools validate` and actionlint. |
| publish | [![publish](https://github.com/ajshastri/chocolatey-packages/actions/workflows/publish.yaml/badge.svg)](https://github.com/ajshastri/chocolatey-packages/actions/workflows/publish.yaml) | On pushes to `master` that change package files (a `*.nuspec` or anything under a `tools/` folder, outside `tests/`), or on demand: validate, pack, test-install and push to Chocolatey. An ungated `check` job runs the checks first; the `choco push` job then waits for approval in the `chocolatey` environment. Dispatched dry runs stop after `check`. |

## Tooling

Package files are maintained with `chocotools`, a standard-library-only Python package in `scripts/chocotools/`. It needs [uv](https://docs.astral.sh/uv/).

```sh
uv sync
uv run python -m chocotools sync --dry-run               # show what would change, write nothing
uv run python -m chocotools sync [--vendor V] [--id ID]  # update nuspec versions, URLs and sha256 checksums
uv run python -m chocotools validate [--online]          # offline checks; --online also checks every download URL
uv run python -m chocotools build [--id ID]              # choco pack into out\ (needs Windows + Chocolatey)
uv run python -m chocotools compare --format md          # repo vs Chocolatey vs upstream report
uv run pytest
uv run actionlint                                        # workflow lint; shellcheck comes from the pinned shellcheck-py dev dependency
```

- `packages.toml` is the manifest: one entry per package (id, folder, vendor, major, image, arch). Packages marked `frozen = true` are skipped by `sync` and `publish` but still checked by `validate` and `compare`.
- `validate` also checks that every install-script URL carries the nuspec version in the vendor's own form (for example Temurin `8.504.1` ↔ `jdk8u504-b01`, Corretto `21.0.12.121` ↔ `21.0.12.12.1`, Zulu distro version ↔ `zulu21.52.203`), so a hand-edited version bump with a stale URL fails CI.
- 5-part upstream versions (NuGet allows 4 parts) are mapped. Corretto `A.B.C.D.E` joins the last two parts (`21.0.12.12.1` → `21.0.12.121`, `21.0.13.0.10` → `21.0.13.10`); a tag with D ≥ 1 and a two-digit E fails, since joining could collide (`1.10` and `11.0` both give `110`). Liberica, SapMachine and OpenJDK `A.B.C.P.E` become `A.B.C.(P*100+E)` (`21.0.13.0.2` → `21.0.13.2`, `27.0.1.0.3` → `27.0.1.3`, `21.0.13.1.1` → `21.0.13.101`); E ≥ 100 fails. If a mapped version equals the repo version but the download URL changed, `sync` fails the package instead of reporting it up-to-date.
- `sync` only writes when the upstream version is higher than both the repo version and the approved Chocolatey version. It uses vendor download URLs and sha256 checksums. A package that fails is reported and its files stay unchanged.
- A package is `pending` (listed under "Pending" in the sync report, not a failure, nothing written) when upstream announced a newer release than its download site serves and the served build is already the repo version. Today only Corretto does this: corretto.aws `latest` decides the build, and a newer GitHub tag waits for it (a tag can be a fix for another platform with no Windows MSI). If the GitHub release is more than 90 days old and still not served, `sync` fails the package. A GitHub tag behind corretto.aws is only noted: the served build is used. `compare` shows these as `pending upstream`.
- HTTP retries: requests to the Chocolatey feed (`community.chocolatey.org`) that get 429/5xx, time out or lose the connection are retried with exponential backoff and jitter (5 s doubling to at most 120 s per wait, honoring `Retry-After`) for up to 15 minutes per request (`CHOCOTOOLS_FEED_RETRY_BUDGET` seconds overrides it). After one request (or `choco push`) uses up that budget, later requests to that host in the same run fail at once, so one outage costs about 15 minutes rather than 15 per package. Other hosts get at most 4 retries (2 s doubling, at most 30 s). Each retry prints one `retry <n> for <host>: ...` line to stderr; other errors such as 404 fail at once. `publish` retries a `choco push` that fails with 429/5xx, a timeout or a connection error under the same feed policy; if a push is told the version already exists (after a retry, or from an earlier run), it counts as done only when the feed or the package's version page lists that version. The workflow jobs have `timeout-minutes` (publish 90, sync 45) with room for one such wait.
- `package_fix = N` with `package_fix_line = "A.B.C"` in `packages.toml` publishes a package fix version when Chocolatey will not take the upstream version again (rejected versions cannot be re-pushed). The fix applies only to upstream versions on the declared line: the 4th segment becomes `P*100+N`, so upstream `21.0.12.1` with fix 1 is `21.0.12.101`, and a later respin `21.0.12.2` is `21.0.12.201`. `sync` removes both lines itself when upstream moves to another `A.B.C` (e.g. `21.0.13`). If the nuspec reaches another line while the fix is still set, `validate` reports the fix as stale; remove the two lines by hand. Details are in `scripts/chocotools/versioning.py`.
- Repository secret `GH_PAT`: fine-grained token with contents and pull-requests write. The sync workflow uses it to check out, push `bot/sync` and open the PR so PR checks run.
- Publish approval gate (one-time setup, repo settings cannot be created from code). Do this before merging the branch that adds the gate: if `publish.yaml` references a `chocolatey` environment that does not exist yet, GitHub creates it without protection rules, and the first publish runs ungated with the repository-level `CHOCO_KEY`.
  1. Settings → Environments → New environment, name it `chocolatey`.
  2. Under Deployment protection rules, tick Required reviewers and add `ajshastri`. Save.
  3. In the same environment, under Environment secrets, add `CHOCO_KEY` (the Chocolatey community API key).
  4. Delete any repository-level `CHOCO_KEY` secret so the key is only released to the approved `publish` job.

  Every publish run first runs the ungated `check` job (`publish --dry-run`: validate, pack, test-install; no environment, no key). The `publish` job then pauses until a reviewer approves it under the run's "Review deployments" button, repeats the checks on the same commit and pushes. Dispatched dry runs end after `check`. The workflow has no concurrency group, so a run waiting for approval never cancels another run's push; each run publishes only the packages its own commit range changed. The push trigger matches `**/*.nuspec` and `**/tools/**` but excludes `tests/**` (the fixtures in `tests/fixtures/pkg/` have nuspecs and `tools/` folders), so a merge that only changes tests starts no publish run and asks for no approval.
- GitHub disables scheduled workflows after 60 days without repository activity. Merging the sync PRs counts as activity.
